# Проверка качества и сравнительные эксперименты

## Три уровня доказательств

1. Структурные проверки: exact bytes, области, ranges, формат и версии. Они необходимы для правильного индекса.
2. Retrieval evaluation: нужные источники и зависимости действительно попадают в пакет с приемлемым количеством лишнего кода.
3. Проверка задачи: объяснение или изменение проходит независимые проверки на точной версии проекта.

Ни синтаксический probe, ни schema validation не являются доказательством второго или третьего уровня.

## Корпус первого эксперимента

Собрать минимум 40 задач одного зафиксированного TypeScript-репозитория: 10 для настройки, 30 для отложенной проверки. Задачи группируются по модулю и похожему сценарию, чтобы близкие варианты не попадали в обе части. Для каждого примера фиксируются repo/revision, tsconfig/dependency hashes, query, ожидаемые units/spans, обязательные dependencies, допустимые дополнительные источники и способ проверки ответа.

Включить адресные запросы, поиск поведения, nested closures, изменение сигнатуры, зависимость от внешнего типа, отрицательный запрос и неполный анализ. Ground truth проверяется чтением исходника и доступным анализатором; для изменений используются реальные ближайшие tests, отдельно от сгенерированного помощником текста.

Частный корпус и исходники не публикуются автоматически. В репозитории достаточно metadata, открытых собственных fixtures и инструкции воспроизведения. Дополнительные TypeScript/C# задачи появляются при разработке соответствующих адаптеров.

## Сравнение вариантов

| Вариант | Дробление | Получение контекста |
|---|---|---|
| A | Фиксированные текстовые окна | Текстовый поиск |
| B | Целые функции | Тот же поисковый канал |
| C | Иерархия AST-блоков | Тот же канал, одинаковый общий бюджет |
| D | Вариант C | Восстановление required context и нужных графовых связей |
| E | Вариант D | Добавление embeddings и проверенного enrichment |

Сначала сравниваются A/B/C, затем вклад D и E. Одновременное изменение модели, дробления и ранжирования не позволяет понять источник результата.

Для каждого запуска фиксируются corpus hash, code revision, config, tokenizer, model/provider при наличии, random seed, budget, retries и результаты по всем задачам. Повторения модельных сценариев одинаковы во всех вариантах. Ошибки окружения учитываются отдельно; неуспешные случаи не исчезают из отчёта.

## Метрики

- Source recall@k и precision: найден ли ожидаемый исходник, сколько нерелевантных записей включено.
- Dependency recall: включены ли обязательные внешние привязки, типы и lifecycle-контейнеры.
- Source correctness: корректны ли snapshot, file, span и content hash цитаты.
- Context sufficiency: достаточно ли пакета для конкретной задачи по ручной rubric.
- Context cost: tokens, лишние bytes, latency, индексирование и модельная стоимость.
- Task success: результат ближайшей реальной проверки изменения или оценка объяснения по rubric.

Similarity score не является метрикой корректности. Перед первым сравнением фиксируется одна основная метрика, остальные служат ограничениями регрессий.

## Критерии перехода

Обязательные gates: 100% точного восстановления на заявленном наборе fixtures; отсутствие незаявленного смешивания snapshot; ни одна заведомо неразрешённая fixture-ссылка не показывается как разрешённая; старый job не перезаписывает новый результат; все выданные источники проходят проверку диапазонов и хеша.

Для качества начальный ориентир D — повышение полноты зависимостей относительно B при одинаковом бюджете и без снижения успешности задач. Численное улучшение выбирается после baseline и до проверки отложенной части. Latency и стоимость публикуются с размером корпуса, машиной и конфигурацией; универсальная скорость заранее не обещается.

MVP можно принять при полезной измеренной выдаче, даже если кандидатное улучшение не победило baseline; в этом случае сохраняется лучший вариант и честно описывается результат эксперимента.

## Обязательные крайние случаи

| Группа | Случаи |
|---|---|
| Исходник | LF/CRLF, UTF-8/BOM, другие кодировки, Unicode, comments, giant literals |
| Синтаксис | Decorators, nested defs, lambda, comprehensions, async, syntax errors |
| Области | Shadowing, global/nonlocal, captures, одинаковые имена, повторные одинаковые блоки |
| Управление | if/else, try/finally, with, ранний return, loop-carried state |
| Семантика | Неизвестный import, dynamic attributes, object mutation, aliases |
| Версии | Rename/move/delete, branch switch, dirty overlay, внешний type или lock change |
| Jobs | Duplicate/retry, lease expiry, late result, projection failure |
| Выдача | Parent/child dedupe, insufficient budget, отсутствующая dependency, пустой точный результат |
| Расширение | C# partial/overload, TSX callback, cross-service contract, доступ разных пользователей |

## Текущие проверки репозитория

`scripts/check_docs.ts` проверяет локальные ссылки, JSON Schema через Ajv2020, согласованность backlog и его dependency graph, сгенерированный Markdown и собственную TS-fixture. `npm run verify` дополнительно выполняет strict TS build, регрессии Unicode mapping / bindings / отклонения повреждённых входов и diagnostic CLI. GitHub Actions повторяет эти checks на Linux и Windows с Node.js 22 и 24. Python для этой проверки не нужен.

Local CM и plugin покрыты `tests/code_memory.test.ts`; `npm run plugin:smoke` строит индекс реального checkout и вызывает четыре tools через настоящие Cordis/SystemPrompt/ToolRuntime 0.2.0-rc.2. Это проверка registry/schema/dispatch/versions/unload, без живого model provider. Она не заменяет 40-задачный retrieval benchmark, проверки Web UI и качества правок.

Distribution entry проверяется реальными Harness bundle/patch consumer functions. Локально tarball также установлен в полный Web-профиль CLI, включая независимый Harness home: профиль boot и четыре registry calls прошли. Это дополнение к автоматизированным checks, с отдельным статусом без живого model loop и browser interaction QA.

Сохранённая проверка FlashMT подтверждает структуру одного примера. Добавлен отдельный [живой Harness A/B pilot](HARNESS-AB.md) на JS-снимке Geo Dash с GPT-6 Luna, exact provider usage и независимыми behavioral checks. Семь holdout tasks и два повтора не заменяют полный 40-задачный benchmark. Полноценный PostgreSQL service и измерения vector/enrichment остаются планом.


Local vector/compact prototype уже проверен настоящим [вторым Harness A/B](HYBRID-RESULTS.md). Primary source/graph остаётся JSON, learned embeddings и vector projection — локальные. Full ledger/FTS, MCP, map UI и broad benchmark остаются планом.
