# Живая CM: пополнение, обновление и поиск

В 0.6.0 добавлен opt-in `autoUpdate`: CM пополняется из **сохранённых TS/JS файлов** настроенного проекта. Локальный агент следит за изменениями; каждый запрос дополнительно проверяет актуальность. В индекс не попадают незаписанные буферы редактора, переписка с моделью, результаты тестов или предполагаемые связи из LLM.

## Что появляется в памяти

Для каждого снимка сохраняются точные исходники, единицы кода, объявления символов и связи компилятора с координатами доказательства. Новая функция создаёт CM-запись; её параметры, локальные имена и используемые определения входят в глоссарий. Вложенные блоки хранятся с владельцем и зависимостями. Векторы — отдельная производная проекция для выбранного `unit`, `window` или `ast` дробления.

У связи `calls` есть исходный диапазон вызова. Сходство векторов остаётся кандидатом для поиска, а inferred topic на карте — группировкой по именам и путям. Они не превращаются в доказанный вызов. Концептуальные описания, проверенные решения из диалога и test evidence потребуют отдельных типов записей, происхождения и admission-проверки; сейчас этот слой не реализован.

## Обновление

```mermaid
flowchart LR
    S[Сохранённые файлы и конфигурация] --> M[Манифест путей и хешей]
    M --> C[Полный compiler rebind]
    C --> G[Код, глоссарий и доказанные связи]
    G --> E[Переиспользование эмбеддингов по fingerprint]
    E --> V[Новая векторная проекция]
    V --> F[Проверка версий и готовности]
    F --> P[Атомарная публикация current.json]
    P --> Q[Поиск в одном снимке]
```

1. Проверяются пути и SHA-256 сохранённых файлов; поэтому замечаются новые файлы, удаления и переименования, а не только изменение времени записи. Игнорируются `.git`, `node_modules`, `dist`, `.artifacts`, `.code-memory`, declaration files и symlinks. `sourceScope` может ограничить дерево, например `game`.
2. В подпись входят корневые package/lock/config файлы и относительные `extends` цепочки `tsconfig`/`jsconfig` внутри проекта. Переключение ветки определяется изменившимся содержимым. Package-based config inheritance и внешние project references пока не имеют полного dependency tracking.
3. Compiler API заново связывает выбранное дерево. Это **полный rebind**, а не частичная подмена AST. Даже маленькая правка может изменить экспорт или потребителей в других файлах; корректность связей важнее неподтверждённого быстрого splice.
4. Эмбеддинги пересчитываются только для новых fingerprint. Fingerprint включает закреплённую модель и подготовленный поисковый текст: имя, путь и ограниченный исходный текст. Сдвиг source span сам по себе не требует нового embedding. Изменённый полный source всё равно получает новую версию, даже если embedding text остался прежним.
5. Новый JSON index и native vectors строятся в отдельном поколении. До публикации проверяются snapshot/model/chunking fences и повторный манифест исходников. Один writer lock и single-flight не дают двум обновлениям одного экземпляра одновременно публиковать состояния. Отмена одного ожидающего запроса не отменяет другого.
6. Готовое поколение публикуется через атомарную замену `current.json`. Source, glossary, graph и vectors относятся к одному снимку. Старый reader держит свою vector lease до завершения; перед выдачей retrieval проверяет, что исходники не изменились во время запроса.

Syntax error, embedding failure или непрерывная запись файлов не публикуют смесь поколений. Старый pointer сохраняется, но запрос к изменённому проекту получает явную ошибку, если свежее поколение ещё невозможно построить. Во время построения допускаются три попытки; foreground запрос может ждать локальную пересборку. Завершённое поколение можно переиспользовать при возврате ветки. Dead writer PID восстанавливается; живой writer ожидается с ограничением 30 секунд.

Обход дерева запускается примерно раз в секунду. Это polling сохранённых файлов, без обязательной интеграции с IDE. Проверка перед запросом закрывает промежуток между опросами. Карта проверяет snapshot раз в две секунды, обновляет modules и очищает старые source/search/graph selections.

## Как потом ищется

Структурный граф и HNSW решают разные задачи. HNSW ускоряет приблизительный поиск соседних векторов. Compiler graph помогает определить, **какой исходный код и определения действительно нужны** выбранной функции.

| Шаг | Действие |
|---|---|
| Freshness | Зафиксировать готовый текущий snapshot, проверить ожидаемый snapshot клиента |
| Named routing | Найти имя/путь в compiler catalog; `adaptive` пропускает dense query при найденном именованном якоре |
| Discovery | Смешать lexical IDF и learned vector candidates, учесть подтверждённых соседей |
| Context | Включить функции и ограниченное замыкание требуемых определений, удалить пересечения, соблюсти source-byte budget |
| Escalation | Если определения не помещаются, явно показать omissions; агент может запросить `detail: expanded` или дочитать точный source |
| Return | Вернуть исходные байты, диапазоны и snapshot; проверить, что source не изменился во время поиска |

Это не «всегда вектор»: точное имя уже даёт сильный сигнал. Semantic discovery использует настоящие локальные эмбеддинги. Схема не вызывает LLM для индексирования или переранжирования. Полнота контекста не обещается: `complete: false` и omissions сохранены. Алгоритм и модельный эксперимент — в [GRAPH-BUDGET](GRAPH-BUDGET.md).

## Подключение

Первый запуск требует локальную embedding-модель. Подготовьте index и vectors по [VECTOR-SEARCH](VECTOR-SEARCH.md); `cm-vector-index` скачивает закреплённую модель при первичной подготовке. Последующие live builds и queries используют локальные файлы модели.

```bash
cm-mcp --project /absolute/project --model-cache /absolute/local-models --auto-update true --memory-dir /absolute/cm-cache/project --retrieval-policy adaptive
```

Для Harness compact config:

```yaml
config:
  projectRoot: /absolute/project
  mode: compact
  autoUpdate: true
  memoryDirectory: /absolute/cm-cache/project
  modelCache: /absolute/local-models
  retrievalPolicy: adaptive
  sourceScope: game
```

`autoUpdate` по умолчанию false для совместимости с ручными snapshots. Его включают для живой работы. Путь `memoryDirectory` находится вне исходников или в `.code-memory`; нельзя положить производные TS/JS файлы в индексируемое дерево. На Windows предпочтителен короткий cache path: native LanceDB сохраняет длинные внутренние имена файлов. `cm-agent` принимает те же настройки и запускает карту, MCP остаётся read-only относительно исходников. [MCP](MCP-SETUP.md), [Atlas](LOCAL-ATLAS.md).

## Проверки и практические пределы

Регрессии `tests/live_memory.test.ts` используют настоящий TypeScript compiler и native LanceDB с детерминированным тестовым embedder. Они проверяют edit/add/rename/delete, связи импортов, синтаксическую ошибку, отказ embedding, изменение source во время построения, реальные Git branches, inherited config, dead writer, scope mismatch, watcher и отмену одного reader. Это отдельно от проверки learned модели на настоящем Geo Dash corpus.

[Learned full-project evidence](../research/evidence/live-cm-2026-10-14.json): 224-file Geo Dash copy, 7503 vectors, реальный Chrome и официальный MCP client — PASS без provider calls. Добавление: 2 новых embeddings / 7503 reuse / 14,48 секунды; правка: 1 / 7504 / 13,66 секунды; rename: 2 / 7503 / 12,56 секунды; delete: 0 / 7503 / 10,78 секунды. Snapshot mismatch, compiler call evidence, semantic discovery, named route и очистка старого UI source проверены. Это измерение одной машины и synthetic addition к настоящему corpus, не гарантия скорости любого проекта.

Дополнительно реальная learned projection с `searchMode: ann` прошла цикл 7503 → 7504 → 7503 rows: новый embedding один, остальные7503 переиспользованы, native `IVF_HNSW_SQ` присутствует после публикации и reopen, semantic query находит reward-policy. Для смены chunking/search mode/model используйте отдельный memory directory; не изменяйте опубликованный vector snapshot на месте.

Локальная стоимость состоит из hashing, полного compiler rebind, сериализации/проверки JSON и создания vector table. Incremental здесь относятся к эмбеддингам; пересборка compiler graph и native projection пока полная. Она выполняется в процессе локального агента и может задерживать ответы. Worker и incremental compiler program остаются следующей оптимизацией, требующей тех же freshness gates.

Готовые и неудачные pending поколения пока сохраняются; bounded retention/GC и crash cleanup не реализованы. Запуск в коммерческом приложении потребует ограничить disk growth, обеспечить восстановление после обрыва питания и проверить network filesystems. Atomic publication проверена на локальной Windows FS, а не заявлена как durability guarantee для всех storage. Неиндексируемые языки, динамические вызовы и зависимости вне настроенного corpus остаются ограничениями.
