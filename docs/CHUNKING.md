# Дробление кода на записи ТМ

## Результат segmenter

Segmenter получает конкретный файл снимка, синтаксическую структуру и конфигурацию. Он выдаёт дерево CodeUnit, выбранную первичную разбивку контейнеров, exact spans, происхождение и диагностику. Глоссарий символов и semantic-аннотации связываются с этими диапазонами отдельно.

Запись для поиска не обязана самостоятельно компилироваться. Она обязана иметь достаточную принадлежность и требования окружения, чтобы контекст можно было восстановить.

## Уровни

1. Файл и тип: контейнеры для навигации, обзора и принадлежности.
2. Функция, метод, callback, lambda: основные реализации и области видимости.
3. Логическая группа инструкций: более точный ответ на вопрос о действии.
4. Выражение и употребление: точечная навигация и evidence, обычно без отдельного embedding.

Иерархические диапазоны перекрываются по принадлежности. У sibling-частей одной первичной разбивки нет перекрытий и пропусков. Аннотации могут охватывать произвольные пересекающиеся участки и не участвуют в восстановлении первичной разбивки.

## Последовательность алгоритма

**Шаг 1. Исходные данные.** Сохранить raw bytes и хеш, установить кодировку. Построить карту координат анализатора к bytes blob. У частично разобранного файла сохранить исходник и диагностику; неизвестную структуру не объявлять полной.

**Шаг 2. Владельцы.** Выделить file, type и callable. У декораторов и атрибутов, сигнатуры, docstring и относящихся к определению комментариев сохранить владельца. Для короткой содержательной функции основной поисковой записью остаётся вся функция.

**Шаг 3. Кандидаты границ.** В большой реализации использовать границы законченных statement-узлов. Первичный baseline разделяет compound statements и объединяет последовательные простые инструкции. Имена функций не определяют их смысловой класс.

**Шаг 4. Уточнение групп.** Оценивать связь определений и употреблений, общий результат, возврат/выход, изменение внешнего состояния и lifecycle-конструкции. Не разрывать связанную цепочку лишь ради точного заполнения окна. Позднее ранжирование границ может учитывать модельные роли, но только среди структурно допустимых кандидатов.

**Шаг 5. Большие узлы.** Рекурсивно раскрывать тело большого compound statement. Родительский `if`, loop, `try`, transaction или context manager остаётся доступным. У дочерней записи сохраняются условие, необходимые ветки и роль cleanup. Для запроса на правку admission контекста может потребовать весь lifecycle-контейнер.

**Шаг 6. Промежутки.** Каждому выбранному срезу назначить trivia согласно одной версии политики: заголовок, комментарии, пустые строки и разделители. Конкатенация первичных частей в исходном порядке должна вернуть исходный контейнер байт в байт.

**Шаг 7. Требования окружения.** Установить внешние привязки, необходимые типы, родителя, guards и доступные разрешённые ссылки. Изменение объекта через метод учитывать отдельно от нового присваивания имени. Alias-анализ имеет собственные ограничения.

**Шаг 8. Поисковые роли.** Присвоить `primary`, `secondary` или `navigation_only`. Глоссарий хранит все поддерживаемые символы, но короткие употребления не становятся миллионами равноправных векторных примеров.

## Бюджеты и исключения

Начальный сравнительный эксперимент использует бюджеты 500 и 1000 токенов выбранного tokenizer, плюс baseline целых функций. Значения служат вариантами эксперимента; оптимальный размер ещё не известен. Фрагмент кода и его восстановленный контекст имеют разные бюджеты.

Маленькая полезная функция не склеивается с соседней чужой функцией. Для неделимой конструкции возможен превышающий бюджет CodeUnit; в выдаче он явно помечен. Крупный литерал, SQL или fixture может иметь вспомогательные подфрагменты, связанные с целым литералом; они не считаются самостоятельно исполняемыми блоками.

## Окружение вложенного блока

Для `nonlocal`, closure captures, `self/this`, generic type parameters и внешних locals сохраняются ссылки на конкретные символы. Для ветки сохраняется выражение guard, для обработчика — try-owner, для кода ресурса — acquire/release-контейнер.

Фрагмент внутри цикла может зависеть от состояния предыдущей итерации. Лексическое чтение/запись не заменяет CFG и reaching-definitions. MVP сообщает доступную глубину анализа, а более полный dataflow вводится отдельным этапом.

## Проверенный пример и пределы текущего probe

В исследовании FlashMT `plan_scene_windows()` разбита на подготовку, вложенную `flush()`, цикл и завершение. Byte reconstruction и внешние привязки проверены; оптимальность границ — нет. Подробности и revision находятся в [исследовании](../research/FLASHMT-ENRICHMENT.md).

Основная собственная [TS-fixture](../fixtures/batching.ts) позволяет повторить структурный сценарий без checkout FlashMT и Python. `npm run probe` после сборки использует TypeScript Compiler API: четыре группы тела, exact bytes и captures `batchNumber`, `batches`, `pending`. Изолированная `flush()` синтаксически допустима, но TypeChecker находит неразрешённые внешние имена. Это другой механизм, чем Python `nonlocal` в исследовании FlashMT.

Текущий TS-скрипт группирует только прямые инструкции выбранной функции; замыкания связываются по compiler symbols, включая проверку shadowed locals. Он не реализует весь рекурсивный segmenter, токенизацию, alias-analysis, cross-file resolution или retrieval. [Python-fixture](../fixtures/batching.py) и исторический probe сохранены только для исследования дополнительного языка.

## Что проверять перед принятием изменения

- Точный raw slice, порядок, непрерывность и восстановление исходника.
- Область и принадлежность каждого блока и употребления.
- Unicode, BOM, CRLF, decorators, nested defs и комментарии у границ.
- `else`, `finally`, loop-carried state и транзакционные границы.
- Очень большие узлы, syntax errors и неподдерживаемая версия языка.
- Отсутствие независимого веса parent/child дублей в поиске.

Проверки выполняются на фиксированных fixtures и затем на размеченных задачах [evaluation](EVALUATION.md).
