# CM в Codex и Claude Code

Раньше CM подключалась к Codex и Claude Code только как MCP-сервер, и экономии не было: модель сама решала, вызывать ли CM, вызывала редко, а вызвав, всё равно читала файлы ([HISTORY.md](HISTORY.md#7-codex-и-claude-code-через-mcp)). Теперь в оба клиента CM подаёт контекст так же, как в Harness: до первого вызова модели, через хук `UserPromptSubmit`.

## Как подключается

`cm-hook` ([src/hooks/cli.ts](../src/hooks/cli.ts)) получает от клиента событие с текстом задачи, выбирает контекст тем же сервисом, что и MCP-сервер, и возвращает `hookSpecificOutput.additionalContext`: инструкцию и блок `CM context`. Формат общий для Codex и Claude Code; для Claude Code в команду добавляется `--client claude`, и инструкция просит править инструментом Edit, а не скриптом в Bash. Установщик ([INSTALL.md](INSTALL.md)) прописывает хук в оба клиента сам. Заголовок не утверждает, что файл «засчитан как прочитанный»: эти клиенты не регистрируют чтение по внешнему контексту. При ошибке хук ничего не добавляет и не мешает запросу.

Codex, `~/.codex/config.toml` или `<repo>/.codex/config.toml`:

```toml
[[hooks.UserPromptSubmit]]

[[hooks.UserPromptSubmit.hooks]]
type = "command"
command = "node /path/to/dist/src/hooks/cli.js --project /path/to/project --retrieval-policy adaptive --auto-update true"
timeout = 120
```

Claude Code, `.claude/settings.json`:

```json
{ "hooks": { "UserPromptSubmit": [ { "hooks": [ { "type": "command",
  "command": "node /path/to/dist/src/hooks/cli.js --project /path/to/project --retrieval-policy adaptive --auto-update true --client claude", "timeout": 120 } ] } ] } }
```

Аргументы те же, что у MCP-сервера ([MCP-SETUP.md](MCP-SETUP.md)): `--index`, `--vectors`, `--model-cache`, `--memory-dir`, `--embedding-cache`, `--source-scope`. Оба клиента требуют доверить хук: Codex — через `/hooks` (в автоматических прогонах `--dangerously-bypass-hook-trust`), Claude Code — как обычные настройки проекта. Переменная `CM_HOOK_LOG` пишет диагностику без исходного кода: маршрут, файлы, размер, время.

### Прогретый демон

Каждый запуск хука — новый процесс. Без помощника он заново грузит индекс (JSON 92 МБ на Geo Dash), векторную модель и LanceDB — около 3,5 с на запрос. Поэтому хук работает через демон ([daemon.ts](../src/hooks/daemon.ts)), по той же идее, что у Netflix с движком IntelliJ ([HISTORY.md](HISTORY.md#10-демон-для-хука)):

- для каждой конфигурации CM (проект, индекс, векторы, модель) — свой демон; он держит всё загруженным в памяти;
- связь — Unix-сокет в каталоге `$TMPDIR/cm-hook-<uid>` с правами `0700`, на Windows — именованный канал; TCP-порт не открывается;
- если демона нет, хук отвечает сам и запускает демон в фоне для следующих запросов; `CM_HOOK_DAEMON=off` это отключает;
- демон не следит за файлами в фоне: перед каждым запросом через индекс он сверяет хеши исходников и при изменениях пересобирает индекс, как и без демона;
- адрес демона зависит и от сборки CM: после обновления или пересборки хук не обращается к демону прежней версии, а поднимает новый; старый завершается сам по таймауту;
- после 30 минут без запросов демон завершается; запустить заранее можно командой `cm-hook-daemon` с теми же аргументами.

| Запрос хука на Geo Dash | Время |
|---|---:|
| Без демона (первый запрос) | 3,5 с |
| Через прогретый демон, поиск места | 0,39–0,63 с |
| Через прогретый демон, названный файл | 0,57 с |

Контекст от демона побайтно совпадает с контекстом, который хук считает сам.


## Методика

Те же шесть задач Geo Dash, рабочие копии, векторы и независимый грейдер, что в сериях Harness ([EFFICIENCY-AB.md](EFFICIENCY-AB.md)); раннер [native_ab.ts](../scripts/native_ab.ts). Три варианта, два повтора, порядок чередуется:

- **без CM**;
- **CM 0.8.1** — как его ставил прежний установщик: MCP-сервер и skill, модель решает сама;
- **новый CM** — хук плюс MCP-сервер и skill из текущей сборки.

Публичная проверка (`project_checks`) дана всем вариантам одинаково — как команда вне рабочей копии. Codex: `gpt-6-luna`, reasoning low, песочница workspace-write; расход — из событий `turn.completed`, цена — расчёт по тарифам Luna. Claude Code: Sonnet 5.5, `--permission-mode acceptEdits`, разрешены Read/Edit/Write/Grep/Glob и только команда проверки; загружаются лишь MCP и хук эксперимента (`--strict-mcp-config`, `--setting-sources project`), без переменных родительской сессии; расход и цена — из итогового события Claude Code. Активация хука подтверждается логом в каждой сессии нового CM, иначе серия останавливается.

### Другие проекты: node-semver и superstruct

Чтобы проверить перенос за пределы Geo Dash, взяты две публичные библиотеки, под которые CM не настраивалась: [node-semver 7.6.3](https://github.com/npm/node-semver/tree/v7.6.3) (48 модулей CommonJS, от коротких функций до `classes/range.js` на 15 КБ) и [superstruct 2.0.2](https://github.com/ianstormtaylor/superstruct/tree/v2.0.2) (TypeScript, 8 модулей до 14 КБ). По шесть задач ([semver](../evaluation/semver/cases.json), [superstruct](../evaluation/superstruct/cases.json)): внесённые ошибки в коротких и крупных модулях, с именем файла, только с именем функции и без имён, и по одному переименованию во всех модулях. Интервалы по парам для токенов не захватывают ноль во всех четырёх сериях, для времени — во всех, кроме superstruct в Claude Code (−3,8…+0,3 с). superstruct в Claude Code — самое слабое место. Серия superstruct в Claude Code повторена на окончательной сборке, со списком вхождений для переименований; до него было −23,7% токенов, цена +1,9%, время −11,5% ([до](../evaluation/native/superstruct-claude-before-results.json)). Первая серия node-semver нашла промах поиска: в caret-zero CM выбирала `testSet` вместо `replaceCaret` из того же `range.js`, потому что у `testSet` больше общих слов с запросом. Вес имени и частота слов запроса нужную функцию не выбирали и портили маршруты других задач. Сработало другое правило: если ни одно имя выбранных корней не отражает запрос, а в уже найденном файле есть функция, в имени которой стоит слово запроса, встречающееся в именах не более двух функций проекта, она добавляется корнем. Из 23 маршрутов изменился только caret-zero: 24К токенов вместо 58К в Codex ([до правила](../evaluation/native/semver-codex-before-results.json)). Данные: [node-semver Codex](../evaluation/native/semver-codex-results.json), [Claude Code](../evaluation/native/semver-claude-results.json), [superstruct Codex](../evaluation/native/superstruct-codex-results.json), [Claude Code](../evaluation/native/superstruct-claude-results.json).

### Переименования: список всех вхождений

Во всех трёх задачах на переименование (rename-day, rename-options, rename-plain) модель с CM сначала искала все вхождения имени: места вызова, которые даёт CM, не включают импорты. Теперь для запросов со словом *rename* CM добавляет список всех мест имени в коде из индекса: определение, импорты, вызовы и ссылки. На всех трёх задачах список совпал с `grep` построчно. Объём исходников в контексте не меняется, у остальных задач контекст прежний.

| Задача | Codex: без CM / CM | Claude Code: без CM / CM до списка / CM со списком |
|---|---:|---:|
| rename-plain (superstruct) | 49К / **42К** | 61К / 79К / 65К |
| rename-options (node-semver) | 89К / **45К** | 125К / 67К / **67К** |
| rename-day (Geo Dash) | 66К / **42К** | 119К / 77К / **86К** |

Codex — по четыре повтора с окончательной формулировкой; Claude Code — по три. В Codex CM дешевле на всех трёх. Claude Code и со списком чаще всего сначала проверяет вхождения сам (Grep), а затем правит каждым Edit по отдельности. Без CM на rename-plain он делает всё одной командой `sed -i` и выходит дешевле. Разрешение `sed -i` в инструкции проверено и отброшено (выше). Подсказка с готовой командой `sed -i` по файлам из списка, только в задачах на переименование, тоже проверена (по три повтора): rename-plain 43К против 65К токенов (цена $0,048 против $0,035), rename-day 103К против 86К, rename-options 170К против 67К; [данные](../evaluation/native/rename-claude-sednote-rn-ss-results.json). Две задачи из трёх дорожают сильнее, чем дешевеет третья, поэтому подсказка не принята.

Разбор записей сессий показал, от чего это зависит. Перед запуском `sed -i` Claude Code проверяет команду и часть таких команд отдаёт на подтверждение («sed command requires approval»); в A/B подтверждать некому, и модель после отказа правит вручную. Отказ получают все команды с `\b` и часть команд без него: `s/validDay/isCalendarDay/g` по файлам Geo Dash — всегда, `s/parseOptions/normalizeOptions/g` по файлам node-semver проходит. Отдельная проверка тех же команд в пустом проекте дала то же. В подсказке CM было `\b`, поэтому на rename-options и rename-day все её запуски получили отказ. Без CM модель на rename-plain пишет команду без `\b`, и она проходит; на rename-day и обычно на rename-options — получает отказ, и без CM эти задачи дороже: rename-options 109–134К против 67К с CM, rename-day 111–134К против 78–130К. CM не может заранее знать, пропустит ли клиент команду, поэтому инструкция оставлена прежней, а проигрыш на rename-plain (65К против 61К) — следствие удачного `sed` без CM. Третья проба — подсказка `sed` без `\b`, только когда имя не входит в другие идентификаторы, и с указанием не повторять отказанную команду (по три повтора): rename-options дешевле (52К против 67К, $0,034 против $0,037), rename-plain меньше токенов, но дороже (43К против 65К, $0,049 против $0,035), rename-day дороже (113К против 86К, отказ клиента); всего по трём задачам $0,152 против $0,134, [данные](../evaluation/native/rename-claude-sedsafe-rn-ss-results.json). Тоже не принята. Если разрешить `sed` в настройках Claude Code (`Bash(sed:*)`), отказов не будет, но это решение пользователя.

### Крупные задачи: функция в трёх файлах, переименование, новый параметр

Три задачи шире одной правки ([larger/cases.json](../evaluation/larger/cases.json)): reward-limit — новый лимит, который проходит через статус квоты, начисление и чтение сохранения в трёх модулях; rename-day — переименование экспортируемой функции во всех импортах и вызовах; depth-body — новый параметр героя во всех проверках контакта. Проверки сверены с эталонными решениями: эталон проходит, исходный код и неполное решение (два файла из трёх) — нет.

Первая серия показала, что CM отдаёт только найденный модуль, и модель ищет остальные файлы сама. Добавлено правило: если запрос просит изменение по всем местам использования (wherever, everywhere, every import, across и т. п.), а найденный модуль показан целиком, CM добавляет функции из других файлов, которые используют его экспорты и совпадают с запросом по словам, вместе с тем, что они вызывают; бюджет таких запросов — в 1,5 раза больше. На запросах без таких слов контекст не меняется: маршруты остальных 15 задач побайтно прежние. Отсюда же вторая находка: Claude Code держит `additionalContext` в переписке только до 10 000 символов (замер на 2.1.312: 9 000 — в переписке, 10 500 — в файле), а больший контекст сохраняет в файл, который модель читает отдельным ходом. Хук для Claude Code теперь уменьшает бюджет, пока контекст не уложится.

### statistics-linear: известная слабость

Задача — ускорить подсчёт частот, сохранив поведение. В исходном коде счётчики строятся объектом, где ключи `1` и `"1"` сливаются, а энтропия считается по `Map`, где они различаются. С CM модель чаще пишет правку сразу и теряет эту разницу: ловушка в 13 сессиях из 24 против 0 из 16 без CM. Проверены две правки инструкции, по пять сессий:

| Вариант | Ловушка | Токены за сессию |
|---|---:|---:|
| Текущая инструкция | 13/24 по сериям | 25–59К |
| + «сохраняй семантику сравнения и ключей (=== против ключей объекта)» | 4/5 | 25–53К |
| Без инструкции, только контекст | 1/5 | 52–111К |

Прямое указание не помогло, а без инструкции модель реже ошибается, но читает и проверяет больше и выходит дороже. Инструкция оставлена прежней. Ошибку ловит публичная проверка, и итоговое качество одинаковое; цена — лишний круг правки на этой задаче.

### Текущая сборка: правка первым вызовом

Две серии прежней сборки выигрывали в сумме, но проигрывали варианту без CM на отдельных задачах: statistics-linear в Codex (+26…+45% токенов в трёх сериях), circle-contact и wallet-delta в Claude Code (+24% и +17%). Разбор сессий нашёл две причины:

1. **Случайный путь в поисковом запросе.** В тексте задачи есть путь к команде проверки со случайным идентификатором прогона (`…/runs/run-9f8e…/project_checks`). Он попадал в векторный запрос и перемешивал ранжирование: на motion-envelope нужный файл иногда вообще не попадал в контекст. Теперь очистка запроса ([focus.ts](../src/code-memory/focus.ts)) убирает абсолютные пути и оставляет от них только имя файла кода. Это касается и обычной работы: пути и команды в запросах встречаются часто.
2. **Лишний вызов модели перед правкой.** Примерно в половине сессий модель первым шагом заново читала файл, который CM уже показала целиком, а правила только во втором вызове. Запрет такого чтения хуком `PreToolUse` (серия ниже) этого не исправляет: отказ — тоже вызов модели. Помогла инструкция хука ([context.ts](../src/hooks/context.ts)): текст файлов точный, контекст для патча копируется из него, правка делается первым же действием, проверка — сразу после неё, без пробного запуска до правки.
