# Как изменять документацию и план

До реализации сохранять различие между предложенным устройством продукта и фактически проверенным поведением. Добавление спецификации, схемы или workflow не означает появления работающего сервиса.

1. Читать [концепт](CONCEPT.md), соответствующую спецификацию и задачу из [backlog](plans/BACKLOG.md).
2. Для изменения контракта обновлять `contracts/core.schema.json`, затронутые примеры и описания API. Не менять смысл поля без версии контракта.
3. Задачи редактировать в `plans/backlog.json`, затем выполнять `python scripts/render_backlog.py`. Не редактировать сгенерированный Markdown вручную.
4. Ссылки на документы этого репозитория делать относительными. Для внешнего исходника указывать репозиторий, revision, путь и строки; не создавать ссылки на диск автора.
5. Запускать `python scripts/check_docs.py`. Если меняется диагностический сценарий, дополнительно запускать `python scripts/probe_flashmt_chunking.py --fixture`.
6. Перед commit проверять diff и список файлов. Локальные артефакты, исходники исследуемых частных проектов и секреты не включать в публикацию.
7. Делать узкие commits. Push, внешние модельные вызовы и выпуск продукта выполнять в пределах разрешения текущей задачи. Проверять фактический remote SHA после отправки.

Проверки этого репозитория охватывают документы, план, примеры контрактов и диагностическую структуру. Они не проверяют качество будущего retrieval, генерацию патчей, работу БД или развёрнутого приложения. Эти проверки вводятся по [плану качества](docs/EVALUATION.md).
